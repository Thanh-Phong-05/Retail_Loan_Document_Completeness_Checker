## TASK 02Q local Confirm integration boundary

Backend uses Java 17, Spring Boot 4.1.2 and the pinned Camunda 8.10.9 starter/client. The checked-in `docker-compose.yml` is a legacy Camunda 8.2 stack and **must not be used** to validate this Confirm path. The opt-in `DurableConfirmCamundaIT` deployed `src/test/resources/workflow/confirm-02q-camunda-it.bpmn` to an isolated real Camunda 8.10.9 engine and passed 1/1 in R6; see `docs/testing/confirm-camunda-it.md` for its setup. That test used H2 and test-only identity/review facts. A separate manual demonstration on Camunda 8.10.10 verified HTTP 202, a completed Confirm operation, READY status, one confirmed audit, and completion of the native User Task and process. Neither test proves integration with the team's BPMN/DMN or production identity/review facts. The R6 live test has not been rerun after R10's persistence mapping changes.

The candidate `docs/db/confirm-02q-sqlserver-additive.sql` passed migration plus Hibernate `validate` on an isolated **synthetic** SQL Server baseline in R9/R10; SQL Server persistence and Vietnamese Unicode tests passed 6/6 in R10. The approved team baseline has not been supplied or migration-tested, and no production schema upgrade was executed. Review the actual baseline before applying this script to an isolated copy. Hibernate defaults to `JPA_DDL_AUTO=validate`, so the app fails startup if required tables are missing. H2 tests use `create-drop` and do not validate SQL Server DDL. The latest full Maven regression on November 21, 2026 passed 131/131 tests. The earlier 137/137 count included nine stale Camunda 8.5 test results from a previous run. Runtime SQL Server startup now requires `DB_PASSWORD` from the environment; no password fallback is stored in `application.properties`.

The real confirmation path also requires a trusted authentication/case-scope provider and authoritative version-bound review facts; neither is installed by default. Do not use synthetic test providers in deployment. The recently merged DMN matches the decision ID and output variable of the unmerged `UNIT02-58` BPMN, whose Confirm User Task ID differs from the current default and whose READY path bypasses that task. The unmerged `UNIT02-22` BPMN uses the current User Task ID but also has a downstream `finalize-completeness-handoff` worker that overlaps READY/audit ownership. No team BPMN has been selected as authoritative. The unmerged `SUB-206.2` frontend sends `reviewerName` and `note` but omits required `expectedVersion` and trusted authentication/CSRF handling. See `docs/api-contract.md` for the provisional 200/202/status behavior, failure states, and integration requirements.
